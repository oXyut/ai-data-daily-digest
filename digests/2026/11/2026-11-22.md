### 1. OpenAI：pretrainingのperplexityをfrontier AIの共通進捗・安全指標へ

- **公開日**: 2026-11-22
- **タグ**: `generative-ai` `machine-learning` `ai-safety` `evaluation`
- **一次情報**: [OpenAI「Perplexity and Intelligence」](https://openai.com/index/perplexity-and-intelligence/)
- **日本語サマリ**: OpenAIのchief scientist Jakub Pachockiは、held-out dataのlog-perplexity（cross-entropy loss）をpretrainingで生まれる潜在能力の共通進捗指標にする案を提示した。社内code dataset上でGPT-3.5は約0.99、GPT-4は約0.91、最近のmodelは約0.76とし、0.8未満でcybersecurity・数学の能力が現れたとの社内観測を説明する。さらに0.68〜0.70付近へ進む前に、lab間の透明性、safety caseのred-team、監視能力に連動した共通の開発上限を整備するよう提案した。
- **重要性・実務上の示唆**: downstream benchmarkが陳腐化・飽和しても継続計測できる基盤指標を、能力予兆と安全gateへ接続しようとする提案である。model調達・risk governanceではperplexity単独を採用せず、domain task、misuse、monitoring、post-training、cost、latencyと組み合わせ、どの閾値で追加評価・release保留・access制御を行うかを事前に定める材料になる。
- **限界**: 数値はOpenAI内部code datasetの固定snapshotに基づき、data mixtureが異なるlab間で直接比較できない。perplexityは実務taskの成功率を直接表さず、chain-of-thought、finetuning、reinforcement learning等のpost-trainingによる能力増加も捉えない。0.68〜0.70の能力予測と安全上限は提案・外挿であり、合意済みstandardではない。

### 2. OpenRouter：推論providerのdata処理incidentを受けZDR適格性を再審査

- **公開日**: 2026-11-22
- **タグ**: `generative-ai` `developer-tools` `security` `ai-infrastructure`
- **一次情報**: [OpenRouter incident公告](https://openrouter.ai/blog/announcements/data-processing-incidents-on-inference-providers/) / [Zero Data Retentionの説明](https://openrouter.ai/blog/insights/zero-data-retention/)
- **日本語サマリ**: 外部researcherの調査で一部推論providerにdata compromiseまたはpolicy不履行の証拠が見つかったとして、OpenRouterは3 providerをoff-boardし、125 endpointをZero Data Retention（ZDR）対象から外し、影響可能性のある顧客へ通知した。OpenRouter自体へのbreachやunauthorized accessは示されていない。今後は同様のtestを継続実行し、network pathを技術検証し、assuranceとvalidationを満たすまでZDRを復元しない方針を示した。
- **重要性・実務上の示唆**: model routerで「ZDR」のlabelだけを信頼せず、実際のrequest経路、再委託先、retention、log、incident通知、provider変更を継続監査すべきことを示す。機密dataを扱うteamはendpointごとのpolicy snapshot、allowlist、request分類、redaction、egress log、fallback時のprovider選択、契約上の通知期限を確認し、ZDR変更をdeployment gateへ組み込む必要がある。
- **限界**: 初報時点で全対象providerは公表されず、顧客別のdata範囲・件数・期間も完全には示されていない。ZDRはproviderによる保存制限であり、routing経路・第三者forwarding・tool call・client側logを含むend-to-end confidentialityの保証ではない。個別providerの報告と顧客通知を別途確認する必要がある。

### 1. 人・robot協働assembly：deep reinforcement learningでtask割当と完了時間を最適化

- **公開日**: 2026-11-22
- **タグ**: `data-science` `machine-learning` `business` `manufacturing`
- **一次情報**: [Scientific Reports原論文](https://www.nature.com/articles/s41598-026-79645-1)
- **日本語サマリ**: 人とrobotが共同で行うassemblyのtask schedulingを、Deep Q-NetworkとModified Red Fox Optimizerで解くframeworkを提案した。論文内のProduct-1・1000分training条件では完了時間74分で、DP 109分、Nash-Q 115分、DQN-SARL 100分、DQN-MARL 82分を下回った。1 human–1 robot構成ではrobot utilization 92.87%を報告し、動的なtask状態に応じて割当を更新する。
- **重要性・実務上の示唆**: 協働robotの導入効果を単体速度ではなく、line全体のmakespan、human／robot utilization、idle time、throughputで評価する設計に使える。pilotでは既存rule-based schedulerと同じorder mixで比較し、安全制約、skill matrix、setup、rework、故障、human overrideをstate／constraintへ入れ、改善が残業・WIP・納期・設備投資回収へつながるかを測るべきである。
- **限界**: 報告値は論文の実験・simulation scenarioに基づき、実工場lineでの長期deployment、safety certification、human fatigue・ergonomics、worker acceptance、integration／保守costは検証していない。製品構成や作業時間分布が変わるsiteへの一般化と、optimizer追加による寄与の独立評価も必要である。

<a id="mine-fragmentation-coa-gpr"></a>
### 2. 露天掘りblast：fragmentation予測をGPRとmetaheuristicで改善

- **公開日**: 2026-11-22
- **タグ**: `data-science` `machine-learning` `business` `mining`
- **一次情報**: [Discover Applied Sciences原論文](https://link.springer.com/article/10.1007/s44290-026-00682-w)
- **日本語サマリ**: 1つのsurface mineから得た573 blast記録を使い、Gaussian Process Regression（GPR）とExtreme Learning Machineを複数のmetaheuristicで調整してrock fragmentationを予測した。70%を5-fold cross-validation付きmodel開発、30%を独立testに分け、COA-GPRはtest MSE 0.00581、R 0.94370、Willmott index 0.93780、PBIAS 6.02%を報告した。baseline GPRのMSE 0.05620から約89.7%減り、SHAPではuniaxial compressive strengthとpowder factorが主要因となった。
- **重要性・実務上の示唆**: blast後の粒度はdrilling、explosive、loading、haulage、crushingのcost・energy・throughputに連鎖するため、設計parameterを事前調整するdecision supportになり得る。導入時は予測誤差だけでなくoversize率、crusher throughput、fuel／energy、explosive cost、vibration、flyrock、安全、model更新頻度を同時に測る必要がある。
- **限界**: 単一mine・573件で、geology・explosive・measurement方法が異なる外部siteの検証はない。Friedman検定はmodel差を示すがpost-hoc pairwise検定はなく、COAの追加複雑性に対する保守費も未評価である。cost、energy、安全、環境影響の実測改善は報告していない。

### 1. fast-anything：app全体でなく遅い関数だけをRustへ移植・再生検証

- **公開日**: 2026-11-21（repository公開）
- **タグ**: `developer-tools` `generative-ai` `performance` `rust`
- **記事原文**: [EL4CTEO/fast-anything repository](https://github.com/EL4CTEO/fast-anything)
- **日本語サマリ**: Python、Node／TypeScript、Ruby、Java、Go、PHP、C／C++のprogramをprofileし、実行時間とportableさでhot functionを順位付けする。最大500件の実callを記録して1-functionのRust crateとagent向けtaskを作り、元実装との値・error・派生edge caseをreplayし、速い場合だけ差し替える。author benchmarkではRuby fuzzy dedupeが3.13秒から228ms（14倍）、Javaが3.50秒から1.18秒（3倍）、C mandelbrotが431msから127ms（3.4倍）などを報告する。
- **重要性・実務上の示唆**: rewriteのscopeをprofileで限定し、agent生成codeをbehavior replayとwhole-app benchmarkでgateするため、performance改善のreview可能性を高める。採用時はprofile再現、representative call、property／fuzz test、precision、FFI／serialization overhead、build・SBOM・license、rollback、p95 latency、resource costをCIとstagingで検証すべきである。
- **話題性**: [Hacker News個別thread](https://news.ycombinator.com/item?id=50596155)で171 points・136 comments、2026-11-22の日別front page 12位を確認。確認日: 2026-11-23 JST。
- **限界**: 性能値はauthorのsample app、i5-10500／Windows 11またはGitHub Actions Linux runnerでの結果で、実serviceを代表しない。記録callの一致は未観測inputやconcurrencyを含む完全な意味同値を保証せず、deterministicでplain dataへ切り出せるhot pathに向く。生成Rustのsecurity・unsafe・依存・保守性は人手reviewが必要である。

### 2. unkernel：実Linux kernelをWebAssemblyへcompileし、未変更aarch64 userlandを実行

- **公開日**: 2026-11-21（v0.2.0 release）
- **タグ**: `developer-tools` `infrastructure` `webassembly` `linux`
- **記事原文**: [pithings/unkernel repository](https://github.com/pithings/unkernel) / [v0.2.0 release](https://github.com/pithings/unkernel/releases/tag/v0.2.0-261121-e69adda)
- **日本語サマリ**: Linux 7.xのkernel、MMU、syscall、scheduler、memory管理、ext4、TCP/IPを単一Wasm moduleへcompileし、未変更のaarch64 Linux binaryだけをinterpreter／JITで実行する。author測定ではNode起動後0.3秒でAlpine prompt、約10MB download、48MiB guest memory。getppidは約170ns（native 110ns）、64-byte readは約170ns（native 160ns）、fork＋exit＋waitは約60µs（native 70µs、QEMU system 1.2ms）とする。
- **重要性・実務上の示唆**: browser／Node内のtraining環境、CLI demo、再現可能test、package実行、agent sandbox候補として、syscall再実装より広いLinux semanticsを持ち込める。採用時は脅威model、host bridge、network egress、persistent storage、resource limit、browser互換、package supply chain、cold start、CPU-heavy workload、licenseを既存VM／container／Wasm runtimeと比較すべきである。
- **話題性**: [Hacker News個別thread](https://news.ycombinator.com/item?id=50533945)で211 points・74 comments、2026-11-22の日別front page 16位を確認。確認日: 2026-11-23 JST。
- **限界**: 数値はauthor benchmarkで、CPU-heavyな`apk search`は約0.8秒、`apk add python3`は約3.4秒とnativeより遅い。networkはhost socketまたはWisp proxyを経由し、server VM／containerと同等のisolationを自動的に保証しない。source buildはZig、Node、clang等と約12分・5GiBを要し、compatibility・security境界は用途別に検証が必要である。
