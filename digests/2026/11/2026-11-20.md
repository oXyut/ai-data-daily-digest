### 1. MedChemBench：創薬の構造読解・実験解釈・化合物選択を99問で評価

- **公開日**: 2026-11-20
- **タグ**: `generative-ai` `machine-learning` `research` `healthcare`
- **一次情報**: [OpenAI公式発表](https://openai.com/index/introducing-medchembench/) / [原論文PDF](https://cdn.openai.com/pdf/2d84f778-f634-5ba7-a3dc-2d3a3b45e3ee/medchembench.pdf)
- **日本語サマリ**: OpenAIは、117本の論文・特許と761種類の分子構造から、医薬化学の99問題を構成したMedChemBenchを公開した。分子構造の再構成、実験根拠に基づく説明、化合物の順位付け・選択、数値物性予測を採点する。xhigh設定でGPT-6.2 Astraは総合84.5%のcreditを得た一方、構造再構成は95.4%でも化合物選択・数値予測は約半分に留まった。
- **重要性・実務上の示唆**: 「化学図を読めるか」と「次に合成・試験すべき化合物を選べるか」を分け、薬効、透過性、代謝安定性など競合する目的のtrade-offを評価する。創薬支援へ導入する場合は、専門家との順位一致、top-k hit率、calibration、実験失敗率、追加合成cost、lead timeを、外部化合物系列とblind評価で測る必要がある。
- **限界**: 公開済み資料への事前接触を除外できず、各回答はtool・feedback・新規実験なしの単発試行である。OpenAI自身も、新薬発見や実験判断の改善を示す結果ではないと明記する。benchmark creditと実験成功率を同一視できず、提供元model中心の評価で独立再現も未確認である。

- **公開日**: 2026-11-20
- **タグ**: `generative-ai` `developer-tools` `cloud` `software-engineering`
- **一次情報**: [AWS公式発表](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-transform-windows-dotnet-11/) / [AWS Transform User Guide](https://docs.aws.amazon.com/transform/latest/userguide/transform-dotnet.html)
- **日本語サマリ**: AWS Transform for .NETは.NET 11対応をGAとし、previewだったVB.NET、WinForms／WPF、XamarinもGAへ移行した。.NET Framework 3.5以降と.NET 5〜10のC#／VB.NETを対象に、class library、ASP.NET、ASMX／WCF、Windows service、test project等を変換する。desktop／mobile以外はLinuxで実行でき、AWSは最大40%の運用費削減可能性を掲げる。追加料金なしで東京を含む8 Regionに提供する。
- **重要性・実務上の示唆**: legacy Windows workloadの棚卸し、code変換、target framework更新をagentic serviceへ寄せ、Linux移行やsupport期限対応の候補を増やす。実案件では自動変換率、未解決dependency、build／test pass率、behavior差分、p95 latency、CPU・memory、license費、運用費、manual remediation時間を変換前後で比較すべきである。
- **限界**: 「最大40%」はAWSの一般的な主張で、workload構成・Windows license・移行工数を含む個別TCOではない。desktop／mobileはLinuxへ移せず、WCF／Web Forms／COM等の互換性、第三者library、認証、data access、性能、rollbackは自動変換だけで保証されない。production切替前の回帰testと段階移行が必要である。

### 1. 株価予測＋exact Shapley：説明可能でもno-skill・buy-and-holdを超えない

- **公開日**: 2026-11-20（early accessの査読済みaccepted version）
- **タグ**: `data-science` `machine-learning` `business` `finance`
- **一次情報**: [Scientific Reports原論文](https://www.nature.com/articles/s41598-026-80656-1)
- **日本語サマリ**: forecast、technical、fundamental、sentiment、riskのsignalを融合し、小さなcoalitionを全列挙してShapley attributionを厳密計算するAgentic-Forecastを提案した。ただしsentiment signalは利用不能で、実験は4 signalとなった。2年のS&P 500／DJIAと、10年・3 index・各約1,800件のout-of-sample decisionをpurged／nested walk-forwardで検証した結果、4 fold平均accuracyは38.70%でmajority-classの44.92%を下回り、多重性補正後はno-skill priorを超えず、売買strategyもbuy-and-holdを上回らなかった。
- **重要性・実務上の示唆**: 「説明が厳密」であることと「予測に事業価値がある」ことを分離し、leakage audit、時系列分割、依存を考慮した推論、多seed、多重検定まで含めてdeployment前の否定的結果を示した点が重要である。金融MLではaccuracyだけでなく、turnover・cost控除後return、drawdown、calibration、regime別性能、benchmark超過を事前登録してgo／no-goを判断すべきである。
- **限界**: 対象は3 indexと設計したsignal群に限られ、個別株・他市場・高頻度・別featureへ一般化できない。一方、baseline gameとconditional gameで最大寄与signalが一致したのは66〜81%に留まり、exactな計算でも説明の参照条件には敏感である。論文自身がlive tradingへの採用を支持しないと明記する。

### 2. UAV物流：transfer node配置とrisk-aware routeを二段階最適化

- **公開日**: 2026-11-20（early accessの査読済みaccepted version）
- **タグ**: `data-science` `machine-learning` `business` `logistics`
- **一次情報**: [Scientific Reports原論文](https://www.nature.com/articles/s41598-026-80467-4)
- **日本語サマリ**: 武漢の都市環境をcase studyに、人口密度・建物高・飛行禁止区域から高度別risk mapを作り、上位層のNoisyNet＋prioritized experience replay付きDDQNでtransfer nodeとservice allocationを、下位層のrisk-weighted Theta*でrouteを同時に最適化する。baseline DDQN比でmean final rewardを22.3%改善し、収束episodeを23.8%削減。通常A*比でservice距離10.5%、risk cost 20.1%、total cost 16.6%を削減した。
- **重要性・実務上の示唆**: node配置と個別routeを別々に最適化して全体costを悪化させる問題へ、distance・risk・service loadを往復させる設計を示す。実証pilotでは配送成功率、cost／delivery、battery余裕、迂回率、risk exposure、騒音、需要変動、再計画時間、regulatory approvalを、地上配送・既存heuristicと比較する必要がある。
- **限界**: 一都市のsimulation／case studyで、実機flight、気象・通信途絶・動的障害物、battery劣化、需要急変、複数operator、住民受容、規制変更を含むproduction評価ではない。報告されたcostはmodel内の定義であり、保険・設備・保守・許認可を含む実TCOへの一般化は未確認である。

### 1. Frostbite：AI agent swarmがISA・compiler・RTL・検証を共同探索したCPU

- **公開日**: 2026-11-18
- **タグ**: `generative-ai` `machine-learning` `developer-tools` `hardware`
- **記事原文**: [Architect Labs公式blog](https://architectlabs.com/blog/frostbite)
- **日本語サマリ**: interaction netを実行する新しいCPUを、agent swarmがcompiler、ISA、microarchitecture、RTL、formal verification、GDSまで反復設計したと報告する。10個のsearch workloadと15個のheld-out workloadを使い、58案中37案を採用。7nm想定のpre-silicon比較で、面積が近い非公開のdual-issue in-order CPU coreに対し、25 workloadの幾何平均でperf/W 4.59倍、held-out 15件で3.83倍、perf/area 8.77倍とする。
- **重要性・実務上の示唆**: agentをcode生成器ではなく、機械検証可能なASL contractをsource of truthにしたcross-stack design searchへ使う事例である。hardware／compiler開発では、候補数、formal property pass率、modelとRTLの誤差、held-out regression、PPA、human review時間をartifactと紐付ける設計が参考になる。
- **話題性**: [Hacker News個別thread](https://news.ycombinator.com/item?id=50572503)で362 points・237 commentsを確認。日別archiveでは一時1位、11月20日の観測の46%でfront page掲載。確認日: 2026-11-21 JST。
- **限界**: 数値は提供元によるpre-silicon評価で、比較CPUは法的理由から非公開。SPEC／PARSEC、out-of-order／multicore CPU、実siliconでの第三者検証はなく、OS・FPGA playground・ISA／RTL公開も今後の予定である。「AIが設計した」という寄与分解も独立監査されていない。

### 2. Linux memory圧縮：zramの実測から、用途別にzswapを選ぶまで

- **公開日**: 2026-11-19（2026-11-20追記）
- **タグ**: `developer-tools` `infrastructure` `performance` `linux`
- **記事原文**: [Curious Bits「Do not buy RAM, compress!」](https://curiousbits.nl/blog/do-not-buy-ram-compress/)
- **日本語サマリ**: 32GB Linux workstationで多数のbrowser tabを開き、zram上で5.7GBを1.7GBへ圧縮（3.35:1）した実例を紹介する。初稿はzramを推奨したが、Hacker Newsでの指摘を受けた11月20日追記で、既存swapの前段cacheとして圧縮するzswapの方が多くの環境に適すると結論を修正した。容量購入の前に、workloadのcompressibility、CPU余力、latency、swap I/Oを測る実務的な入口になる。
- **重要性・実務上の示唆**: AI開発でbrowser、IDE、container、local toolを並列実行する端末や、CPUに余裕があるmemory-bound serverでは、hardware増強前の検証候補になる。memory pressure、compression ratio、CPU、p95 latency、major page fault、swap I/O、OOM、SSD write量、costをzram／zswap／disk swap／増設RAMで比較すべきである。
- **話題性**: [Hacker News個別thread](https://news.ycombinator.com/item?id=50557661)で322 points・266 commentsを確認。記事本文もHacker News掲載と、議論を受けた結論修正を明記する。確認日: 2026-11-21 JST。
- **限界**: 1台・browser中心の観察で、cloud cost半減は未検証の回想的推測である。圧縮はCPUとlatencyを消費し、既にentropyが高いquantized LLM weight等には効きにくい。zramとzswapの適否はswap構成・I/O・workloadで異なり、productionではOOM・latency・SSD enduranceを含む負荷試験が必要である。
