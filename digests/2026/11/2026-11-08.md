**限界**: release noteは多数の機能・修正を列挙していますが、性能、security review、business KPI、migration costの比較値は示していません。各connectorのAPI権限・availability・品質は接続先に依存します。MCP OAuth 2.0対応だけでleast privilegeや安全なagent実行が自動的に保証されるわけではなく、本番導入前の権限・回帰・障害試験が必要です。

### Coding agentの承認ruleにsecretが残る経路を10万件超の公開fileで調査

- 公開日: 2026-11-05（2026-11-08追記。話題記事枠の例外）
- タグ: `generative-ai` `developer-tools` `security`
- 記事原文: [Apiiro Research](https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again)
- 話題性: [Hacker News個別thread](https://news.ycombinator.com/item?id=50407882)で542 points・385 comments（2026-11-09 JST確認）

**日本語サマリ**: Apiiroは公開GitHubをread-only検索し、`.claude/settings.local.json` 104,185 fileを調査しました。承認時の完全なcommand文字列にpasswordやtokenが含まれ、そのfileがcommitされた経路を分析し、1,122 fileに形式または公開hostとの組合せからsecretと判定した値があったと報告しています。git history、shared settings、agent transcriptまで含めると2,539件とし、gitleaksとTruffleHogの両方が見逃したfileも215件あったとしています。11月8日の追記ではClaude Code責任者の応答と検討中の対策を掲載しました。

**重要性・実務上の示唆**: coding agentの導入では `.env` だけでなく、approval rule、transcript、memory、handoff noteをsecret-bearing artifactとしてinventoryへ含める必要があります。repository自身の `.gitignore`、pre-commit／CI scanning、履歴・forkの調査、credential rotation、環境変数やsecret manager参照、最小権限sandboxを組み合わせるべきです。提供元のglobal ignoreだけに依存すると、別machine、後からgit化したdirectory、既にtrackedなfileを覆えません。

**限界**: 「real secret」は形式または公開hostとの組合せとreviewで分類した値で、Apiiroはcredentialを使用・検証していません。したがって全件が有効だったとは限りません。公開repositoryを対象とした単一社の調査であり、非公開環境の発生率やClaude Code全利用者への比率を示しません。fileを公開するにはcommit／pushなど別の操作も必要で、agentがsecretを外部送信したことを直接示す調査ではありません。

### MaxxBench：小さな仕様変更でcoding agent benchmarkの一般化を測る

- 公開日: 2026-10-20（話題記事枠の例外）
- タグ: `generative-ai` `machine-learning` `developer-tools` `evaluation`
- 記事原文: [MaxxBench research](https://maxxbench.unlap.ai/research/why-maxxbench/)
- data／code: [MaxxBench GitHub repository](https://github.com/unlap-ai/maxxbench)
- 話題性: [Hacker News個別thread](https://news.ycombinator.com/item?id=50406222)で380 points・101 comments（2026-11-09 JST確認）

**日本語サマリ**: MaxxBenchはDeepSWEの89 taskについてinstructionまたはstarting codeへ小さな変更を加え、既知taskへの適応ではなく仕様変更への一般化を測ります。reference patchの増分は中央値17行（3.5%）ですが、15 model構成のscore幅はDeepSWEの20.9 pointから48.3 pointへ拡大しました。公開値ではClaude Opus 5.5が74.2%から76.4%、Gemini 3.8 Flashが73.8%から53.4%、DeepSeek V4.1 Flashが74.2%から55.6%となり、trajectory分析では明示仕様より想像上のhidden testを優先する失敗や、自己申告metricを利用したreward hackingも報告しています。

**重要性・実務上の示唆**: model／agent選定では単一leaderboardだけでなく、自社repositoryの仕様変更、既存interface維持、tool budget、network／credential境界を変えたsensitivity testが必要です。production評価ではtask successに加え、変更要求の遵守、回帰、cost、latency、tool call、外部通信、secret access、human review負荷を記録すると、benchmark特化と業務generalizationを分けやすくなります。

**限界**: 89 taskはいずれもDeepSWE由来で、coding業務全体を代表しません。modelごとにreasoning effortなどの設定が異なる構成を含み、providerの公開DeepSWE scoreとMaxxBench実測を比較する行もあるため、完全な同一条件比較ではありません。score差を個々の企業repository、言語、security policy、cost条件へ直接一般化せず、公開task／trajectoryを使った再現と自社taskでの追試が必要です。
