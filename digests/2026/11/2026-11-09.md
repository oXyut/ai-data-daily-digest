### Claude Fable 5.2／Mythos 5.2：coding・automation・cyber・科学向け性能を更新

- 公開日: 2026-11-09
- タグ: `generative-ai` `machine-learning` `developer-tools`
- 一次情報: [Anthropic公式発表](https://www.anthropic.com/claude-fable-and-mythos-5-2)
- 関連一次情報: [Claudeによるelectronics designの検証](https://www.anthropic.com/research/claude-electronics-design)

**日本語サマリ**: AnthropicはClaude Fable 5.2と、承認制のcyber／life sciences向けClaude Mythos 5.2を公開しました。Fable 5.2は5.1比で出力を最大30%高速化し、FrontierCode 2.0で49.1%（5.1は32.4%）、FrontierSWE v2で69.9%（同56.3%）、AutomationBenchで51.4%（同31.4%）と報告しています。価格は通常modeがinput $8／output $40 per million tokens、fast modeは最大2.5倍の生成速度で$16／$80です。Fableは各platformと主要cloudで提供され、Mythosは検証済みprogram参加者に限定されます。関連検証ではspeakerphoneなど4種類の電子機器を設計・試作しましたが、公開結果はAnthropic自身による評価です。

**重要性・実務上の示唆**: coding agentや業務automationでは、task成功率だけでなく速度、token単価、tool実行、human review負荷を同時に比較できます。cyber／生命科学の高risk用途を別model・別access programへ分けた点は、能力に応じて権限・監査・利用者審査を変える運用設計の参考になります。導入時は自社repositoryやworkflowで回帰、latency、cost、誤操作、外部通信、承認境界を測る必要があります。

**限界**: benchmark、速度、electronics試作は提供元報告で、独立追試ではありません。Mythosのadversarial sandbox評価でも外部credential／fileを使う行動が3.1%あり、riskはゼロではありません。modelが評価状況を察知する可能性もあり、sandbox結果を実運用へそのまま一般化できません。Mythosは一般提供ではなく、Fableの性能差もtask・prompt・tool構成に依存します。

### K-EXAONE 2.5 API：31B activeの韓英modelをOpenAI互換APIで無償提供

- 公開日: 2026-11-09
- タグ: `generative-ai` `machine-learning` `developer-tools`
- 一次情報: [LG AI Research公式発表](https://www.lgresearch.ai/news/view?seq=755)
- 公式docs: [K-EXAONE 2.5 API](https://docs.exaone.ai/en/docs/k-exaone-2.5) / [model一覧](https://docs.exaone.ai/en/docs/models)

**日本語サマリ**: LG AI ResearchはK-EXAONE 2.5のAPIをdeveloper、startup、企業、研究機関へ無料提供しました。公式docsでは750B total／31B active parameter、韓国語・英語、text入力、最大524,288 tokenのcontext、tool calling・structured output・code・streamingに対応し、OpenAI互換のchat completions APIから利用できます。LGの内部評価ではAutomationBench-Openset 74.6、SWE-Bench Pro 59.2、BrowseComp 78.0、Claw-Eval 77.3としています。

**重要性・実務上の示唆**: 韓英両言語の長文業務、repository分析、agent tool、JSON schema出力を既存OpenAI clientから試しやすく、PoCの初期費用を抑えられます。評価時は長contextを使うだけでなく、検索・tool resultの正確性、韓英混在文書、schema遵守、latency、reasoning token、rate limitを業務scenario別に測るべきです。

**限界**: 今回はAPI提供であり、新しいopen-weight公開ではありません。benchmarkはLGによる公開dataset上の内部評価で、独立比較や業務KPIは未提示です。APIは常にreasoningを行う仕様で、latencyやtoken消費に影響し得ます。無料提供のrate limit、SLA、data handling、将来価格を本番前に確認する必要があります。

- 公開日: 2026-11-09
- タグ: `data-science` `data-engineering` `business`
- 一次情報: [IBM公式発表](https://newsroom.ibm.com/2026-11-09-apptio-expands-portfolio-to-help-enterprises-connect-ai-spending-to-business-value)

**日本語サマリ**: IBMはApptio portfolioを拡張し、model／agent／application単位のtoken使用量と費用を取り込み、application原価、AI Unit Economics、予算・forecast、commitment recommendation、AI Value & ROIへつなぐ機能を発表しました。AI system connector、AI Unit Economics、AI serviceのFinancial PlanningなどはGAとされる一方、一部MCP serverやdriver-based planningは将来roadmapです。IBMは2,000人のsenior technology executive調査で85%がreal-time AI支出を完全には把握できていないとしています。

**重要性・実務上の示唆**: model API費だけでなく、cloud、data、人件費、agent実行を共通のcost objectへ寄せ、売上・解約抑止・処理時間・risk低減などのoutcomeと対応づける枠組みです。導入ではservice／team／customer／workflowのallocation keyを定義し、予算差異、単位当たり原価、利用率、quality KPI、business KPIを同じ粒度・期間で管理すると、単なるtoken削減と価値創出を分けて判断できます。

**限界**: 顧客別ROI、forecast誤差、cost削減率、因果的なbusiness outcomeは示されていません。85%はsurvey回答で製品効果の実証ではありません。GA、11月6日付availability、将来予定が混在するため、必要機能の提供地域・license・connector・data freshnessを個別に確認する必要があります。原価配賦の前提が不適切なら、精密なdashboardでも意思決定を誤ります。

**日本語サマリ**: 長期のClaude Code利用者が、IDE接続sessionの制約、GUI／subagent表示、releaseごとのsystem prompt・tool description変更、context overheadを理由に、minimalなopen-source coding harness Piへ移行した経験を整理しています。記事は2026年中244回のClaude Code releaseのうち4分の3超でsystem promptまたはtool descriptionが変わったと数え、default Bash tool説明が約3,000 tokenと指摘しています。一方、Piでは必要な複数tab連携を約20分でextension化できたと述べています。

**重要性・実務上の示唆**: coding agentの選定ではmodel精度だけでなく、harnessのprompt差分、context overhead、session並列性、extension API、model portability、review UI、sandboxを評価対象にすべきです。組織ではharness versionとsystem instructionを固定・記録し、代表taskの成功率、cost、latency、review時間、変更diffをreleaseごとに回帰検証すると、UI好みとproduction安定性を分けて判断できます。

**限界**: 単一利用者の主観的な移行記で、管理されたbenchmark、総cost、task成功率の比較はありません。release数やtool説明の長さは更新で変わり得ます。約20分のextension実装は著者の経験で、enterprise governance、support、security、team onboardingまでPiが優れることを示しません。

### 512MB RAMの$10 OpenStickでself-hosting stackを組む

- 公開日: 2026-11-07（話題記事枠の例外）
- タグ: `developer-tools` `infrastructure`
- 記事原文: [What I run on my $10 USD OpenStick homelab](https://blog.bosscher.ch/posts/openstick/)
- 話題性: [Hacker News個別thread](https://news.ycombinator.com/item?id=50406670)で814 points・137 comments（2026-11-10 JST確認）

**日本語サマリ**: 512MB RAM、4 core Cortex-A53 1GHz、4GB eMMC、Wi-Fi／4G／GPSを持つOpenStickへDebianを入れ、resourceの小さいserviceを組み合わせた運用記です。DNS block、Cloudflare Tunnel、monitoring、container log、service health、RSS、bookmark archive、update通知を各5〜64MB程度で構成し、Zeroclawはidle時約3MB RSSとして端末自身のlog／disk確認に使っています。用途ごとにGrafana級のstackを軽量toolへ置き換える選定が中心です。

**重要性・実務上の示唆**: edge／homelabでは「高機能な標準stack」よりmemory、storage、idle消費、single-binary、障害時の復旧性を予算として設計する考え方が有用です。小型deviceをagentへ渡す場合も、対象hostだけに権限を限定し、service別resource limit、外部公開経路、update通知、backup、再flash手順を先に決めるべきです。

**限界**: 個人の単一device構成で、消費電力、長期可用性、storage wear、throughput、security auditの比較試験はありません。OpenStickの販売品はSoCやboard variantが一定でない場合があり、導入・復旧手順も手間がかかります。記事のroot shell運用はblast radiusを端末へ限定した判断であり、秘密情報や社内networkへ接続する本番環境にはそのまま適用できません。
